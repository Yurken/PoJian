# 破茧 Emerge：音频优先的短视频回顾规划

状态：音频优先原型已实施（v0.4.0），真机与参赛效果评测待完成。更新日期：2026-10-08。起始代码基线：v0.3.1 / `c127d1a`。下文保留规划目标，实际交付见本节。

### 本轮交付与边界

- 已实现音频/视频音轨导入、单应用播放声音采集、端侧中文 Zipformer 转写、分段时间、暂停/继续/停止；模型按用户操作下载并校验固定版本。
- 音频会话与转写迁移到 Room v3，原始/修订文字分别保存，接入原有记录与本地分析；音频时长不计观看停留。删除、修订和迟到任务采用版本检查，历史变化后相关回顾失效。
- 可选文字服务网关已实现，支持通义或自建兼容模型，客户端/服务端均检查逐字引文；默认关闭、只在手动回顾时发送文字，支持每日调用上限。
- 当前限制单次前 5 分钟；只保留文字，不支持原声留存/回听。使用流式识别端点分段，未增加独立 VAD。语义任务由用户手动触发，未做自动批次或跨视频归并。
- 已有公开中文样例真实识别及工程测试；下文的 10 分钟连续输入、20 段质量对照、真机耗电、CER/F1 和参赛效果尚未完成，不能视为已有成绩。测试详情见 [构建与验证](../BUILD_VALIDATION.md)。

## 1. 摘要

初版采用“手机取得播放音频 → 本地小模型转文字 → 观点与依据分析 → 与历史比较”的路线。先让破茧理解短视频中的口播，复用现有文字记录和回顾能力，控制采集、推理与存储开销。

语音识别优先在手机本地运行；复杂语义判断可选文字 API，之后再评估自部署文本模型。画面、图表和字幕视觉识别作为后续扩展。本版定位为“音频与可见文字驱动的信息回顾”。

## 3. 当前基础与可行性

规划起点 v0.3.1 已有授权应用范围、无障碍文字记录、停留估计、今天 / 7 天回顾、离线文字规则分析及删除功能。原数据库版本为 2；本轮音频能力与 v3 迁移已实现。

音频先转成文字，可以接入现有信息回顾流程。相较同时处理画面和声音，这条路线减少了视频编码、抽帧、OCR 和视觉模型调用环节；实际耗电仍需在真机上测量。

### 播放音频如何取得

Android 10 起提供 AudioPlaybackCapture。跨应用内录需要 `RECORD_AUDIO`、MediaProjection 用户授权、同一用户配置，并要求来源播放器允许捕获。实现可以只读取播放音频，不创建画面捕获链路或视频文件。系统授权流程仍存在，具体目标平台是否允许内录需实测。[Android 播放音频捕获文档](https://developer.android.com/media/platform/av-capture)

用户主动开始和结束一次会话；权限撤回、应用范围变化或系统终止时停止处理。仅匹配所选应用的音频 UID，避免把其他应用同时播放的声音混入。静音流要区分“没有语音”“无音轨”和“无法取得音频”，不能据此补写内容。

初版有两个输入入口：

- **导入音频**：先跑通本地转写与分析，也是展示备用入口。后续可以接受用户提供的视频文件并仅提取其音轨。
- **记录一段浏览**：用户授权后，实时接收所选应用的播放音频并转写。

遇到不允许内录的应用，提示导入用户持有的文件或继续使用现有可见文字记录；麦克风录音应当作为单独、明确开启的功能，不能自动替代内录。仅有分享链接时，不保证可以取得其媒体文件。

## 4. 目标与验收

初版交付“可用的轻量语音输入 + 可核查的文本判断 + 有对照的数据”，以下均是验收目标，尚无实测成绩。

| 目标 | 验收方法 |
| --- | --- |
| 能在目标手机持续转写 | 连续处理 10 分钟口播，平均处理速度快于音频产生速度，无持续积压 |
| 资源开销可接受 | 测量模型加载、峰值内存、CPU、温升、30 分钟额外耗电；与同手机正常播放对照 |
| 关键语义不被听错带偏 | 除中文字错误率 CER 外，单独检查否定词、数字、时间、地点和人名错误 |
| 判断可以查回来源 | 每条关键判断绑定转写片段与时间；保留音频的片段可点击回听 |
| 重复与新依据能区分 | 在独立标注集报告分类 F1、重复误报率及未知比例，对比现有规则和直接 API 判断 |
| 用户可停止、删除和纠正 | 停止即停止采样；删除后待处理结果不能写回；纠正转写后相关分析失效并重新计算 |

选择模型时先保证核心内容识别质量，再比较模型文件大小和速度。未通过关键语义检查的片段不用于生成确定的观点关系。

## 5. 使用场景

优先覆盖中文口播、知识讲解、访谈和新闻评论。例如，用户连续刷到几段就业话题，回顾时希望知道这些视频是在反复说同一结论，还是补充了新的数据和条件。

纯画面表达、字幕独占信息、图表细节和无声视频的覆盖有限；报告明确自己的音频 / 文字观察范围。音乐、舞蹈、搞笑等内容保留题材或未知状态，不强行提取观点或评判价值。

## 6. 用户价值与参赛亮点

| 需求 | 初版输出 | 可验证的贡献 |
| --- | --- | --- |
| 回想刚才听了什么 | 带时间的转写和简短要点 | 手机端轻量采集与转写流程 |
| 区分作者观点与引用 | 观点、引述 / 反驳关系及原句 | 考虑转写误差、上下文和证据的判断 |
| 看出有没有新信息 | 旧观点、新依据、条件补充或材料复述 | 分开比较观点与依据的历史增量算法 |
| 回顾自己的信息环境 | 重复接触和新增依据的时间线 | 可追溯的个人历史比较 |

参赛主张围绕资源开销、证据可追溯和信息增量展开。小模型转写属于基础能力，项目自研部分应体现在分段、证据约束、误差处理和历史比较上，并以实验展示实际改进。

## 7. 解决方案

### 7.1 主流程

```mermaid
flowchart LR
    A[授权播放音频 / 导入音频] --> B[缓冲、重采样、语音分段]
    B --> C[手机端小模型转写]
    C --> D[带时间的稳定文字]
    D --> E[规则 / 可选文字 API]
    E --> F[观点、依据与历史增量]
    F --> G[回顾与原句核查]
```

语义分析只接收已经稳定的转写，避免每次临时识别结果变化都触发请求。建议先按完整语句合并，每 20–30 秒或用户结束会话后分析一次；对引用后反驳保留上下文并支持修订。具体批次大小由延迟和费用实测调整。

### 7.2 小模型选型

**优先验证 sherpa-onnx + 中文流式 Zipformer 小模型。** sherpa-onnx 提供 Android 本地识别实现，不要求转写时联网。[Android 支持文档](https://k2-fsa.github.io/sherpa/onnx/android/index.html)

| 候选 | 用途 | 选择条件 |
| --- | --- | --- |
| 中文 Zipformer 小模型，量化配置 | 首选轻量流式原型 | 目标手机的普通话口播、数字和否定句识别达到可用水平 |
| 中文 / 中英 Paraformer 流式量化版本 | 质量与性能对照 | 第一候选的错误影响下游判断时比较替换收益 |
| Vosk small-cn | 较小模型的基线 | 用同一组音频测量后决定是否采用 |

具体起步候选为 `sherpa-onnx-streaming-zipformer-zh-14M-2023-02-23`。官方文档所示量化示例配置包含约 21 MB 编码器、7.2 MB 解码器和 1.7 MB 连接器，合计约 30 MB；这是模型文件量级，未包含推理库、词表和运行内存，也不是准确率保证。[模型与配置](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/online-transducer/zipformer-transducer-models.html)

Paraformer 有流式 int8 路线；Vosk 的中文小模型下载包标为 42 MB。它们仅作为候选，不凭名称中的 small 或量化标签推断真实耗电和识别质量。[Paraformer 文档](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/online-paraformer/index.html) · [Vosk 模型列表](https://alphacephei.com/vosk/models)

先准备 20 段、每段 30–60 秒的有权使用音频，覆盖清晰普通话、背景音乐、快语速、数字、否定、少量中英混说。用相同输入比较 CER、关键语义错误、速度、内存和温升，再锁定模型版本。

### 7.3 音频处理与保存

使用 AudioRecord 取得播放音频，按模型要求重采样和转为单声道；可先采用 16 kHz、16 bit PCM 的处理格式。VAD 用于减少静音推理，同时保留句首和句尾，避免把重要词截断；持续音乐、歌词和多人重叠需要单独评测。

设置有上限的音频缓冲与推理队列。处理跟不上时提示延迟并记录缺失，不无限堆积；不把漏掉的时间自动记为已识别。音频处理时间使用单调时钟，再映射到记录时间。

默认采用短时缓冲，转写稳定后释放原始音频，仅保存文字和时间。用户可选择“保留原声片段”，用于回听和核查，并设置容量上限及自动到期。仅保存文字时，界面说明它是自动转写；不能提供已经不存在的音频回放。

费用控制来自本地转写、批量文本分析、相同结果复用及日 / 月限额。ASR 无按分钟 API 费用，但仍消耗手机资源；文字 API 费用用实际 token 与调用次数计算。

### 7.4 文字判断与自研算法

**第一步：统一文字入口。** 将语音转写与现有可见文字接入同一分析接口，同时保留来源区别。绑定原始 ASR 文本、人工修订文本、时间和识别状态，修订不能覆盖掉核查依据。

**第二步：抽取观点与依据。** 本地规则先形成基线；用户选择云端增强后，将必要的转写与少量历史候选发送至文字 API。输出讨论对象、观点、依据原句、适用条件、引述 / 反驳关系及未知原因。所有引文必须能对应输入片段。听不清的数字、否定或主体不能由模型自行补全。

**第三步：比较历史。** 先按议题、地区、时间和人群条件找可比内容，再分别比较观点与依据，区分相同观点的新依据、条件补充、解释深化、旧材料复述和未知。相似度用于找候选，不直接决定重复。所有比较按浏览发生时间计算。

缺少画面和账号元数据时，不能可靠推断作者身份、数据来源独立性或完整视频立场。单纯根据声音变化或一句话结束，也不能确认用户已经划到下一条视频。第一版将不确定边界保存为“音频片段”；若能从既有无障碍信息取得标题、来源和页面变化，再辅助归并。

云端处理可通过简单的服务端适配器接入文字模型，API 密钥保留在服务端。后续需要更强数据控制时，可以用同一接口替换成自部署文本模型。初期不需要同时维护视觉模型和 GPU 推理集群。

### 7.5 App 与数据改动

保留“概览 / 记录 / 设置”三页。

- **概览**：增加“记录一段浏览”与“导入音频”；显示处理进度和回顾。
- **记录**：增加“语音转写”来源，展开后查看分段原句、时间与识别状态；原声仍在时可回听。
- **设置**：模型准备状态、音频来源范围、原声保存策略、可选文字 API、费用上限。

在现有 Kotlin、Compose、Room 上新增 `AudioSession`、`TranscriptSegment` 和 `AnalysisJob`，设计从数据库版本 2 的无损迁移。片段包含会话、来源应用、时间区间、原始 / 修订文字、模型版本、可选音频引用和缺失状态。

同一时段的无障碍文字与口播应关联到同一观察窗口，避免双倍计算停留时长。导入文件只计作提交的材料，其时长不能直接推定为历史观看时长。删除时同时取消任务并使迟到结果失效。

离线模式继续保留本地处理。云端增强开启时，要明确会发送哪些文字，并同步更新现有“不会上传”的适用范围；语音在本地转写不意味着后续云端文字分析也在本地。

### 7.6 评测与三分钟展示

评测分成两层：先评价 ASR，再评价判断。对同一段内容分别使用人工校对文字和 ASR 原始文字进行分析，量出语音错误对观点 / 增量判断的影响。

语义对照包括现有规则、文字模型直接判断、加入证据约束和历史比较的方法。测试重点为数字变化、否定词、引用后反驳、同观点新依据及同材料换说法。测试素材按原始来源分组，开发与测试集合避免同源片段泄漏；独立复核并记录分歧。

建议的展示流程：

1. 开始一段授权播放音频记录，或导入准备好的音频。
2. 看到本地转写逐步产生，结束后生成观点和依据。
3. 加入另一段相近口播，展示“结论相同、依据新增”。
4. 再加入一段复述，展示历史关联并点开原句；已保存原声时可回听。
5. 展示目标手机的转写性能和人工复核结果，并说明尚未覆盖的情况。

## 8. 实施阶段

| 阶段 | 预计工作量 | 交付 |
| --- | --- | --- |
| P0 音频与模型验证 | 2–3 天 | 目标应用内录可行性、20 段音频对照、模型大小及真机资源记录 |
| P1 本地转写流程 | 约 1 周 | 音频导入、所选应用播放音频采集、分段转写、状态与删除 |
| P2 判断与历史比较 | 约 1 周 | 规则基线、可选文字 API、证据原句和增量分类 |
| P3 参赛打磨 | 约 1 周 | 真机长会话、转写误差评测、对照结果与展示流程 |

在内录与模型可行性通过的前提下，初步估计约 3–4 周形成参赛原型；目标平台受限、转写质量不足或设备适配会影响周期。先完成可测的小流程，再决定更大模型或服务端转写是否有必要。

后续扩展顺序为：更好的转写与条件判断 → 用户主动提交截图的 OCR 补充 → 有明确收益时再加入画面理解。时序图学习和机密计算保留为独立研究方向。

下一步是在目标真机验证目标应用内录、资源与转写质量，并完成独立标注的语义对照。P1 与 P2 的原型工程已落地，P0 的真机质量测量和 P3 的参赛效果验证仍需完成。
